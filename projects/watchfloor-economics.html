Economics & model routing

Autonomous pipelines have a cost curve. I measure it before I decide anything.

Watchfloor chapter 4 of 4 · Solo project, actively evolving
model routing a/b testing ollama cost tracking

Every phase of the pipeline can run on a different model. Which model each phase gets is not a guess: it's the outcome of controlled experiments that run the same feature through the same pipeline on different configurations and compare cost, speed, and quality. The result so far is a 56% cost reduction with every quality gate intact.

Why cost is a governance problem

An unattended pipeline spends money with nobody watching. That makes cost a supervision concern, not an afterthought: the same discipline that gates quality has to gate spend. It also has to be measured honestly, which turned out to be the first problem. Early cost numbers came from a summary file that missed failed attempts and re-runs. One baseline run that really cost $38.01 would have reported as $10.76 on the dashboard. Before optimising anything, I had to build cost accounting that dedupes phantom events and counts retries. If the measurement is wrong, every decision built on it is wrong too.

The experiment

The question: can cheaper models do part of the pipeline's work without lowering the bar? Rather than guessing from benchmarks, I ran canaries. Three configurations implemented the exact same feature through the same eight-phase pipeline, each in its own isolated worktree, halting at the same phase. Same spec, same gates, different economics.

A Opus baseline $38.01
Strongest model on every phase fastest in API time · most expensive
B Sonnet on every phase $18.35
Mid-tier model throughout 52% cheaper · all gates passed
C Sonnet + Haiku, compact context $16.78
Mid-tier for reasoning, small model for mechanical phases 56% cheaper · all gates passed · now the default

Three canaries, one feature spec, one pipeline. Costs measured end to end with retry-aware accounting. Configuration C became the default routing.

The winning configuration routes the reasoning phases (requirements, design, test planning, review, implementation, QA) to a mid-tier model and the mechanical phases (static analysis, commit) to a small one. The premium model earns its price on latency, not on outcomes this pipeline can't already verify. That finding only holds because the gates are deterministic: with tests, type checkers, and adversarial review deciding what passes, the model choice becomes an economic decision instead of a leap of faith.

Routing is layered like any rollout policy: a per-task override in the execution plan, a per-invocation override on the command line, a per-shell default, and a documented way to disable it entirely. Partial overrides are honored, so a single phase can be re-routed without redefining the rest.

Routing to local models

The same routing machinery can send selected phases to a local model server (Ollama) instead of the API. It's strictly opt-in, and with the flags unset the behaviour is byte-identical to the default path, which keeps experiments honest. Two phases are denylisted from local routing by design: review and QA always run on the strongest available models. The phases that judge the work are the last place to save money.

I have to report this one as a failed experiment, at least for now. The local server advertises compatibility with the same API the pipeline speaks, but real runs against the agent harness broke in ways the documentation didn't predict, and the models my hardware could serve struggled under even the lighter phases. The plumbing works. The economics don't, not on my hardware today. The harness stays in the codebase because the denylist thinking and the byte-identical default cost nothing to keep, and local models keep improving. Parked, not abandoned.

Cheaper turns, not just cheaper tokens

Model price is only half the cost curve. The other half is wasted turns. Reading the session metrics showed that a quarter to a third of all shell commands in unattended runs ended in an error, and the agents' default response was to retry with small variations, including on errors that can never succeed, like operations the sandbox blocks by design. Now a hook classifies every shell error into one of seven categories, and the pipeline's rules tell the agent exactly which categories are worth a retry and which mean move on. The compact predecessor context described in the autopilot chapter attacks the same curve from the context side: agents that load less irrelevant text answer faster, cheaper, and more accurately.

Reflections

This chapter is where the solo project looks most like an organisational one. Model routing policies, measured baselines, controlled canaries, override hierarchies with a paper trail: this is the shape of AI cost governance at any scale. The 56% number matters less than how it was reached. A vendor benchmark would have suggested the same direction, but the canary made it a decision I can defend line by line, on my own workload, with my own quality gates as the referee. That's the standard I would hold an organisation's AI spend to, because it's the standard I hold my own to.

What went wrong

Not every efficiency idea survived contact with measurement. One documented optimisation reduces how much a model deliberates before acting, promising large output-token savings at benchmark parity. I wired it in behind a flag and ran two canaries side by side, identical except for that flag. The run with reduced deliberation produced plausible-looking work and then failed to commit it: it skipped the careful final pass where the agent checks that everything it changed is actually staged and merged. The twin run with the flag off committed cleanly. The saving was real, and so was the cost of the corner it cut. The flag ships in the codebase, off by default, with the canary evidence documented next to it. Some optimisations are cheaper thinking; this one was skipped thinking.
