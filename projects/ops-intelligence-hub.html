Ops Intelligence Hub

BI dashboards show what happened. This one tells you what to do about it, and shows its working.

Solo project · Built from February 2026 solution design · mid-flight
python fastapi langgraph react typescript postgresql openai

A solution design, mid-flight. Built and tested: deterministic workforce analytics, AI recommendations that trace back to the numbers behind them, and a person who approves before anything goes further. Built but not finished: a synthetic organisation and a simulation loop meant to test those recommendations over time.

  • The process: the capacity and budget analysis a manager does by hand in spreadsheets.
  • The problem: BI dashboards show what happened. Managers need what to do about it, with reasoning they can audit.
  • The decision: deterministic analytics produce the numbers, AI only interprets them, and each recommendation traces to the computed results behind it.
  • What I built: a workforce decision-intelligence hub, a deterministic synthetic organisation with test scenarios built in, and a turn-based simulation loop.
  • What I learned: this is where autopilot was built. Backend work ran unattended through the pipeline while I focused on the judgement calls.
  • Why it matters: separating what the AI generates from what verifies it, the same pattern that runs through everything here.

The questions behind the design

The first design question was where AI makes sense and what has to stay deterministic. Here the numbers come from fixed calculations, and the AI explains them and recommends, because a model that does the arithmetic gives figures nobody can reproduce. That only works when the data is in order. Without order in the data there is no automation, which I learned the slow way (see What went wrong). A recommendation also has to be explainable to the person it affects, so each one carries references to the computed results behind it and waits for a person's approval. And since real workforce data is off limits, the system is tested on a synthetic organisation with known problems built in. I would expect any organisation that puts AI into a management process to meet the same questions.

Where it stands

  • Built and tested: 11 deterministic analytics modules, the three-agent LangGraph pipeline, the evidence gate on recommendations, the human approval gate, the synthetic organisation, and an MCP server exposing eight analytics tools and two report exports.
  • Built, not yet wired: the simulation loop. It runs turn by turn against the real pipeline, but the LLM-generated life events that should make outcomes vary are not connected in the running app.
  • In progress: observability (the stack is configured, nothing is instrumented yet), analytics reconciliation, UI unification, and scoring of live agent output. Today only the analytics are evaluated against the real code.
  • Verified: 1,600+ automated tests (Python + TypeScript), green as of August 2026.
  • Known limitations: a localhost tool with no authentication layer, and insight-card values and the summary text are not yet evidence-gated the way recommendations are.

How it started

I've spent years accounting for where hours went, arguing for budget adjustments, and fighting time registration structures that were too fine-grained to be useful. The data existed, but the analysis was always manual: spreadsheets, gut feel, and executive summaries that cherry-picked data points with no traceability. I wanted to build the analysis tooling I wished I had.

What it does

The system has three layers, and the separation between them is the point.

01 Analytics deterministic · no LLM
Capacity & utilization overload, bench, allocation balance
Budget & cost groups variance, two-layer allocation model
Absence & overtime type classification, systematic overwork
Data quality missing data, rounding errors, time leakage
Outliers & forecasting statistical anomalies, capacity projections
Config-driven dispatch configuration decides which analytics run, not a model

11 analytics modules. Deterministic by construction, with no clock, no randomness and config-driven thresholds. Same input, same output, every time.

02 Agents LLM · LangGraph
Insight agent turns computed results into insight cards
Action agent generates recommendations grounded in evidence
Reporting agent executive summaries for stakeholders

Recommendations are evidence-gated: every evidence reference is matched against the computed results. Unmatched references are stripped, and recommendations without evidence are dropped. The text the model writes around them is not number-checked yet.

03 Human gate approve · reject · adjust
Approval with LangGraph interrupt() graph pauses, surfaces reasoning, waits for human decision

Default mode gates every recommendation, and a timeout auto-rejects. It never auto-approves. In that mode no AI recommendation reaches a stakeholder without documented human review. Evidence is immutable after approval.

When someone challenges a recommendation ("Why should we move two people to Team B?"), the claim traces through the agent's reasoning, through the tool call, down to the analytics module, metric, entity, and period that produced the number.

Two systems, not one

The OIH system analyses workforce data and recommends actions. But how do I test whether those recommendations are any good? I needed a second system: a synthetic world that the first system operates on, where I can run scenarios, observe consequences, and reset to baseline.

GDPR constraints meant I couldn't use real workforce data. So I built a synthetic organisation: roughly 250 employees across six departments in a fictitious Nordic fintech, with five years of planning data (allocations and norm hours; budgets cover three) and two-plus years of realised timesheets and absences. The data generator is deterministic: same seed, same output, every run. The current build has 139,000+ timesheet rows.

Seven problem scenarios are specified, and five are demonstrably in the generated data, among them the ML Platform team at 112–130% overload in the second half of 2024 and Backend Core with 40% missing timesheet entries. Portfolio budget pressure and external dependency concentration are not there yet. All seven are patterns I've seen repeatedly over 25 years, and the data is a test harness designed to stress every analytics module.

Building on synthetic data turned out to be an advantage, not just a GDPR workaround. The scenarios are reproducible, the analytics modules can be tested against known ground truth, and the whole system can be demonstrated without access to anyone's actual workforce data.

Simulating decisions

Static test data can verify that analytics modules compute correctly, but it can't verify that the system handles a changing organisation over time. The simulation engine is meant to close the loop: take the OIH system's recommendations, apply them to the synthetic organisation, and play the consequences forward.

Organisational decisions don't land cleanly. Moving two people to a new team doesn't guarantee full productivity on day one, and hiring takes longer than planned. The design is for an LLM to generate that variation in outcomes. What runs today is the loop itself: turn by turn against the real OIH pipeline, approved actions applied to a copy of the synthetic organisation, and the scenario compared with the baseline. The LLM-generated life events are written but not connected, so every action lands exactly as planned, and each turn re-projects the same period. Carrying earlier decisions forward month by month is the next step.

Design decisions

  • No classifier, no dynamic routing. The graph is fixed, and configuration decides which analytics run. A classifier adds latency and failure modes for no benefit when the set of analyses is known.
  • No vector database. The data is 100% structured, so RAG would add complexity without value. EuLex is the RAG project.
  • Config-driven thresholds. All business rules in YAML, not code. "Over-allocated" means 110% or more, and that number lives in a config file.

What went wrong

The biggest lesson: I should have started with the data. I built analytics modules, agent orchestration, and UI components before the synthetic data model was solid. That meant constantly retrofitting as the data shape changed. Everything in a system like this starts with data. The structure of the timesheets, the allocation model, the absence categories. Getting those right first would have saved weeks of rework. It's the kind of mistake that sounds obvious in hindsight, but the pull to build the interesting parts first is strong.
