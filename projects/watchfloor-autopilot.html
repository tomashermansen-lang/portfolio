Autopilot & execution graphs

Unattended delivery for work where the gates are sufficient. Dependency-ordered plans for work bigger than one feature.

Watchfloor chapter 2 of 4 · Solo project, actively evolving
bash tmux yaml json schema

Three orchestrators run the pipeline without a human in the loop: autopilot for one task, autochain for a whole plan, and grinder for continuous codebase improvement. Execution graphs coordinate the work, carry context between tasks, and measure when the implementation drifts from the plan.

Running unattended

The commands are the same as in interactive work. How they're orchestrated differs:

  • Flow mode. For work that needs human judgement: UI features, ambiguous requirements, anything where I want to review output before it propagates. I move through phases conversationally, approving each one.
  • Autopilot. For backend work where the deterministic gates are sufficient. The entire pipeline runs unattended in tmux. Same agents, same review cycles, same static analysis gates, but all human checkpoints auto-approved. A failed run resumes from the phase that broke, not from scratch.
  • Autochain. Autopilot at plan level. It walks an execution graph and runs every eligible task through its own pipeline, in parallel where dependencies allow, with gates between phases and configurable behaviour on failure.
  • Grinder. A continuous improvement loop that runs outside the feature pipeline. It discovers findings across the codebase and works through them in passes: mechanical cleanups, static analysis findings, coverage gaps, and dependency vulnerabilities.

One rule holds across all of them: checkpoints being auto-approved changes nothing else. Same gates, same review depth, same standards. Autonomy is not a quality discount.

Autopilot auto-approving a commit checkpoint. Tests pass, merge to main, cleanup.

Execution graphs: coordinating what a single pipeline can't

"Plans are worthless, but planning is everything." — Dwight D. Eisenhower, remarks to the National Defense Executive Reserve, 1957

The pipeline handles one feature at a time. A real module might need a data layer, an API, business logic, and a UI, each depending on the others, each running through its own requirements-to-QA cycle.

Execution graphs are the coordination layer for this. Via /plan-project, work gets broken into structured YAML plans with phases, tasks, dependency chains, and quality gates, validated against a versioned schema. Each task is a feature that enters the pipeline independently. Tasks within a phase can run in parallel. Tasks across phases respect dependency ordering. Each task also carries an autopilot eligibility flag: backend work with clear acceptance criteria runs unattended, while UI work stays in flow mode with human checkpoints. The same team-based review pattern applies here. /plan-project --team brings up to eight specialist agents into the planning process itself, poking at the scope and dependencies before any code is written.

I'm not naive about upfront planning. Nobody can predict everything at the start, and detailed plans drift the moment they meet reality. But execution graphs are useful for a different reason: they force me to think about scope, sequencing, and dependencies before writing code. Even when the plan changes (and it will), having made the plan reveals the right questions early. When reality does drift from the plan, /plan-project --update reconciles the graph with what actually happened, preserving completed work while re-sequencing what remains. The cost of replanning is minutes, not days. That changes how willing I am to change direction mid-project.

A simplified example of what an execution graph looks like in practice:

01 Foundation gate: all tests pass
Data layer autopilot
API layer autopilot
Configuration autopilot

All three run in parallel, no dependencies between them.

02 Core logic gate: tests + static analysis
Business logic autopilot · after data layer
Integration tests autopilot · after business logic

Sequential, each task unblocks the next.

03 Interface gate: e2e tests + manual QA
UI components flow · after API layer
End-to-end wiring flow · after business logic

Parallel, both need human review, so both run in flow mode.

Each task enters the full pipeline independently, /start through /commit. Tasks marked autopilot run unattended. Tasks marked flow pause for human checkpoints. The gate between phases must pass before downstream work begins.

Context flows across the graph

The execution graph doesn't just order tasks. It also controls what each task knows about the others. When a task depends on completed work, its phases automatically load a compact context block that the predecessor persisted on completion: the decisions it made and why, the interfaces it exposed, a summary of what actually changed, and a map of the functions and classes it touched with their line ranges. The agent navigates the predecessor's work through that map instead of pulling whole files into context.

The compact block replaced full artifact reads for a measured reason: long, loosely relevant context makes models less accurate while costing more, a pattern documented in context-rot research and visible in my own runs. Each phase gets the context profile it needs. Requirements analysis reads only the decision summaries; implementation also gets the interfaces and the symbol map. Nothing downstream inherits an upstream session's reasoning or mistakes.

Data layer completed DONE
Decision shadow what was decided, and why
Interfaces what it promises to callers
Change summary + symbol map what changed, where to look, line by line
UI layer starting depends on: data layer
/ba reads the decision shadow knows what the data layer promised and delivered
/implement adds interfaces + symbol map navigates predecessor code without loading whole files

Only the compact context block crosses the feature boundary, tuned per phase. Implementation details stay encapsulated.

Watching for drift

A plan is a contract, and unattended work needs someone checking the contract. After each phase, a deterministic heuristic compares what was implemented against what the task promised: how many files changed versus planned, how much code, and how much of the acceptance criteria the work actually covers. Tasks within tolerance pass silently. Flagged tasks go to a dedicated assessor agent that classifies the drift into a defined taxonomy (scope creep, scope cut, reinterpretation, and nine other categories), with a confidence score and evidence quoted from the artifacts. Drift is measured, not felt. The watch floor shows the verdicts alongside the plan.

Reflections

Autonomy here was never one big decision. It accumulated: first one phase unattended, then one task, then chains of tasks with gates between them, then continuous improvement passes running in the background. Each step was backed by the previous step's evidence. That's the pattern I would bring to an organisation: not "should agents work autonomously" as a yes-or-no question, but a ladder of autonomy where each rung is earned with an audit trail. The infrastructure that lets me trust an unattended run (deterministic gates, drift measurement, resumable failures, full session records) is precisely the infrastructure a team would need, at a larger scale.

What went wrong

Autopilot went through two redesigns in about two days. The first version tried to scrape tmux terminal output to track what the pipeline was doing. I wanted the full history including hooks, permission prompts, everything. It kept breaking on ANSI escape codes and partial output. I went through many iterations trying to make it work before discovering that Claude Code already writes a structured log of every action it takes. Once I switched to reading that data, the core of autopilot came together quickly. The lesson was simple: I spent two days fighting scraped terminal text when the structured data was already there.

The grinder taught a quieter lesson. During one long unattended run, the CLI's authentication expired mid-loop. The orchestrator interpreted every failure as transient, retried, and ended up reverting its own commits. Nothing was lost except hours, but the failure mode was embarrassing: a supervision system that couldn't tell "temporarily broken" from "not allowed in". Grinder now probes authentication before starting and emits a structured event that stops the retry loop the moment credentials fail. Autonomous systems need to know the difference between an error they can work through and one that means stop.
