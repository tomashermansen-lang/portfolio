The watch floor

If I'm going to let AI agents run unattended, I need to see what they did and why. Increasingly, I also need the controls to act on what I see.

Watchfloor chapter 3 of 4 · Built from February 2026, actively evolving
react typescript python fastapi mui recharts

The supervision deck that gives the system its name. A full-stack dashboard for monitoring autonomous pipeline runs, navigating multi-task projects, and providing the audit trail that makes unattended AI work accountable. What began as pure observability has grown a control surface: pause, resume, and a terminal into any running session.

How it started

Once execution graphs existed, I needed a place to see the plan and monitor how it was going: which features are done, which are in progress, and which need my attention. The first version was a single HTML file with inline JavaScript. A bash hook registered with Claude Code fired on every session event and appended a line to a shared log file. The HTML page polled that file through a small Python server and rendered session cards. Two days later, execution plans arrived in the pipeline and the requirements changed completely. The rewrite to React with a Python backend took longer than building the original.

What it monitors

The plan viewer renders execution graphs as visual dependency trackers. Phases expand to show their tasks, each with a progress bar showing how far through the pipeline it is. Gates show whether pass conditions are met, and drift verdicts from the deviation assessor appear alongside the tasks they concern. This is the primary view for larger projects: which phases are done, what's blocked, where the project actually stands.

Plan viewer: execution graphs with phases, dependency connections, and task states. Tap to expand.

The dashboard also shows all active sessions across projects. Click a session and VS Code opens the relevant worktree automatically, so I can jump straight into the code. When several features run in parallel, this is how I know where my attention is needed: sessions waiting for human input get a pulsing indicator and sort to the top.

The autopilot monitor discovers active autopilot sessions by scanning project directories for pipeline output files. Each session gets a phase stepper and cost tracking per phase. Pipeline state at a glance, session details one click deeper.

Session viewer with a live pipeline run. Session list on the left, streamed output on the right. Tap to expand.

The session viewer is the drill-down. Click any session, flow mode or autopilot, and the viewer shows what happened inside it. For active sessions, it streams the agent's output in near-real-time: phase transitions, tool calls (collapsible), the agent's reasoning, and results. For completed sessions, it's a full replay of the run.

Task detail: pipeline phases, requirements, testplan, and artifact chain.

Session metrics came later, once I realised the hook data could feed back into the process. Eight panels cover tool usage, error rates, session lifecycle, permission friction, subagent utilization, file activity, task completion, and an activity timeline. When a run fails or takes too long, the metrics show where time and tokens went.

Session metrics: KPI strip at the top, activity timeline, tool usage, error tracking, and more. Tap to expand.

From observing to controlling

The dashboard was read-only by principle for its first months: it never wrote anything, anywhere. That constraint kept the architecture simple and made the early trust question easy, since a monitoring tool that can't act can't do harm. But real supervision eventually needs hands. When an unattended run heads somewhere it shouldn't, watching it go wrong is not oversight.

So the watch floor grew a control surface, deliberately narrow. Autopilot sessions can be paused and resumed from the dashboard, with a state machine guarding which transitions are legal. An embedded terminal connects into the live tmux session over a WebSocket, so intervention happens in the same session the agent is using, on the record, rather than in a side channel. The backend moved from a small standard-library server to FastAPI as part of this shift. Reads are still cheap file reads with no database. Control actions are the only writes, and each one is explicit.

Hooks handle event generation. The backend reads, and acts only when told to. The watch floor observes and, when needed, intervenes.

Session discovery is automatic. The backend scans project directories for pipeline output files and execution plans. No configuration file, no session registration. Start a pipeline run and the watch floor picks it up.

Reflections

The session data turned out to be the only complete audit trail for unattended runs. Git shows the outcome, commits and merged code, but not the path that got there: which tools the agent called, which files it read, which approaches it tried and abandoned, what ruff and mypy flagged, what SonarQube reported, how the agent responded to each finding. The watch floor captures and persists the full stream per feature, so I can review exactly what happened in any autopilot run after the fact. When AI agents write code autonomously, someone needs to be able to answer the question: "What did it actually do?" This is that answer.

I didn't trust autopilot mode until I could watch it. The dashboard wasn't a nice-to-have that came after the pipeline was complete. It was the thing that unlocked actually using unattended runs. And the same evidence later justified each control: pause came from the times I watched something drift and had no better option than killing the session. The metrics feed the improvement loop too. Patterns in how agents spend time and turns became the cost and routing work in the next chapter.

The pattern I keep coming back to is the same one organisations will face as AI-assisted development scales: structured observability over autonomous work, clear audit trails, and human oversight that doesn't require watching every step. This is a solo setup, but the governance questions are the same ones a team of fifty will hit.

What went wrong

The HTML-to-fullstack rewrite was the biggest early time sink. The original HTML dashboard went up in a day and worked for session monitoring. Two days later, execution plans arrived and the requirements changed completely: visualising task dependencies as graphs, computing phase progress, evaluating gate conditions. Vanilla JavaScript couldn't handle that.

ANSI escape codes in session data were the other pain point. The backend reads output from pipeline runs that include terminal colour codes, cursor movements, and control sequences. There is no definitive list of all ANSI sequences. I built the stripping regex iteratively: run a session, find garbled text in the dashboard, identify the escape sequence, add it to the pattern, repeat. Dozens of iterations before the session view rendered cleanly.

And the "read-only" principle itself aged into a small lesson. It was the right constraint for building trust, and I held onto it a little past its usefulness, the same way I held onto the two-repo split. Principles that earn their keep early still deserve re-examination when the system around them changes.
